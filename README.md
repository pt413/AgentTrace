# AgentTrace

> Build multi-agent workflows visually, run them against local or hosted agents, and inspect every step of an execution.

AgentTrace is a full-stack developer tool for composing AI-agent pipelines and understanding what happened when they run. It pairs a drag-and-drop React workflow editor with a FastAPI execution engine that records structured, span-level traces. The result is a practical environment for prototyping agent systems without losing visibility into inputs, outputs, timing, failures, and model token usage.

## Why I built it

Agent applications are rarely a single model call. They are pipelines: prompt preparation, model calls, data extraction, transforms, custom services, and branching paths. When one of those steps fails or produces an unexpected result, a final answer alone is not enough to diagnose it.

AgentTrace makes that execution path visible. A developer can assemble a workflow, connect their own HTTP-compatible agents, run the graph, and drill into the trace generated by each invocation.

## What it does

- Design workflows on a visual canvas by adding agents and connecting their input/output handles.
- Run built-in utility agents or registered local/online HTTP agents in the same workflow.
- Support OpenAI-compatible Chat Completions endpoints for LLM nodes.
- Pass each node's output to downstream nodes and handle fan-out and repeated deliveries.
- Record a workflow root span plus one child span for every agent invocation.
- Inspect span hierarchy, inputs, outputs, model, token counts, latency, metadata, status, and safe error details.
- Register, edit, and delete external-agent connections without exposing credentials to the browser.
- Validate workflow configuration before external requests are made and retain failed runs as traces for debugging.

## Product walkthrough

1. Open **Workflow** and add built-in or external agents from the library.
2. Configure each card, then connect agents either by dragging handles or through the connection dialog.
3. Provide a text or JSON starting input and run the workflow.
4. Review terminal outputs immediately, then open **Execution traces**.
5. Select any span in the execution graph to inspect the exact recorded invocation and diagnose success or failure.

The editor intentionally starts empty, so workflows are explicit and easy to reason about.

## Built-in agents

| Agent | Purpose | Key configuration |
| --- | --- | --- |
| LLM agent | Sends the current value to an OpenAI-compatible Chat Completions endpoint. | Endpoint, model, system instructions, optional backend environment-variable name for an API key |
| Prompt template | Wraps incoming text or JSON using `{{input}}`. | Template |
| JSON extractor | Reads nested object fields or array items from JSON. | Dot path, e.g. `items.0.text` |
| Text transformer | Normalizes or changes the case of text. | `trim`, `uppercase`, or `lowercase` |

External agents may use either the Agent JSON contract below or a Chat Completions-compatible API.

```text
│ • run input and results         │◀─────────────│ Trace service + in-memory stores    │
│ Trace list, graph & inspector   │              └──────────────┬─────────────────────┘
└────────────────────────────────┘                             │
                                                                 ▼

                                                    or Chat Completions providers
```

### Execution model

The backend uses a queue-based scheduler. Without an explicit entry agent, every node with no incoming edge receives the starting input. With one selected, only that node and its reachable descendants run. Each output is delivered to every outgoing connection. If a node has multiple incoming deliveries, it is invoked once per delivery; branches are not implicitly merged or run in parallel.

Cycles are supported when an entry agent is selected. Safety limits stop runs at a configurable step limit (30 by default, 100 maximum), after 120 seconds of total runtime, or after an agent failure. Every attempt—including loop iterations and failures—receives its own span so the trace remains faithful to the execution.

## External agent contract

For the default `agent_json` protocol, AgentTrace `POST`s the following payload to the configured endpoint:

```json
{
  "input": "previous agent output",
  "context": {
    "trace_id": "...",
    "node_id": "...",
    "step": 1
  }
}
```

The agent responds with an object containing `output`, which may be any JSON value:

```json
{
  "output": {
    "answer": "Agent result"
  }
}
```

For `chat_completions`, configure a full compatible endpoint and model. AgentTrace sends `{ model, messages, stream: false }` and reads `choices[0].message.content` from the response.

There is a runnable example endpoint at [`backend/examples/local_agent.py`](backend/examples/local_agent.py).

## Run locally

### Prerequisites

- Python 3.10+ and `pip`
- Node.js 18+ and npm

### 1. Start the API

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

The API is available at `http://localhost:8000`, its health endpoint is `/`, and interactive OpenAPI documentation is at `http://localhost:8000/docs`.

### 2. Start the frontend

Open a second terminal:

```powershell
cd frontend
npm install
Copy-Item .env.example .env
npm start
```

Open `http://localhost:3000`. The frontend defaults to `http://localhost:8000`; set `REACT_APP_API_BASE_URL` in `frontend/.env` if the API is hosted elsewhere.

### 3. Optional: run a sample external agent

In a third terminal, from `backend/`:

```powershell
python -m uvicorn examples.local_agent:app --host 127.0.0.1 --port 9000
```

In AgentTrace, choose **Local agent** and register `http://localhost:9000/invoke`. Add that agent to the canvas and run it like any other node.

### 4. Optional: load demonstration traces

Set `AGENTTRACE_DEMO=true` in `backend/.env` before starting the API. This seeds trace data only; it does not pre-populate the workflow editor.

## Configuration and secrets

`backend/.env` is loaded for local development, while environment variables supplied by the deployment platform take precedence. Keep provider credentials there or in the platform secret manager:

```env
AGENTTRACE_DEMO=false
OPENAI_API_KEY=
```

For an LLM or external agent, enter only the variable name (for example, `OPENAI_API_KEY`) in AgentTrace. The backend reads that value and sends it as a Bearer token. No keys are returned by the catalog, stored in browser state, or written into trace configuration. Never put secrets in `REACT_APP_*` variables: those values are bundled into the client.

## Safety considerations

- The local development API has no authentication—bind it to loopback, as shown above.
- Only complete `http://` or `https://` endpoint URLs are allowed; credentials, query strings, and fragments are rejected.
- Online agents require HTTPS; local/self-hosted development services can use HTTP.
- Redirects are not followed, and HTTP error bodies/URLs are omitted from recorded errors to avoid leaking credentials.
- Request bodies, agent responses, and outputs are capped at 2 MB; requests time out within 60 seconds.
- Inputs and outputs are intentionally retained for trace inspection, so connected agents should never echo secrets.

## API overview

| Method | Endpoint | Description |
| --- | --- | --- |
| `GET` | `/` | Service health check |
| `GET` | `/api/v1/agents` | List built-in agents and external registrations |
| `POST` | `/api/v1/agents/external` | Register an external agent connection |
| `PUT` | `/api/v1/agents/external/{id}` | Update a registered agent |
| `DELETE` | `/api/v1/agents/external/{id}` | Remove an external agent |
| `POST` | `/api/v1/workflows/run` | Validate, execute, and trace a workflow |
| `POST` | `/api/v1/traces` | Create a trace and its spans |
| `GET` | `/api/v1/traces` | List trace summaries |
| `GET` | `/api/v1/traces/{trace_id}` | Retrieve a trace with all spans |

The generated API reference at `/docs` is the authoritative request/response schema.

## Current scope and next steps

AgentTrace is intentionally a focused local-development prototype. External-agent registrations, traces, and canvas state are in memory, so they reset when the backend or browser restarts. It does not yet provide authentication, multi-user workspaces, database-backed persistence, parallel scheduling, automatic branch joins, marketplace installation, or direct execution of repository/skill URLs.

The clearest production evolution would be persistent storage, user authentication and access controls, asynchronous/parallel execution, configurable trace retention/redaction, workflow save/share/versioning, and deployment adapters for external agent ecosystems.
